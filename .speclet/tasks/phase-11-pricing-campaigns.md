# Phase 11: Pricing Campaigns

Status: Not Started
Source: plans/02-business.md #20-21; plans/03-domain-model.md #19-21,23; plans/04-user-flows.md #28-30; plans/05-pricing-engine.md #10-11; plans/06-product-requirements.md #37-39; plans/07-database.md #32-33

## Tasks

- [ ] **Define the `campaigns` entity** — Create a campaign data model with fields `shop_id`, `name`, `status`, `pricing_rule_id`, `start_at`, `end_at`, `created_at`, `updated_at`. Status must be one of `DRAFT`, `SCHEDULED`, `ACTIVE`, `COMPLETED`, `CANCELLED`, `FAILED`. A Campaign is a business event (when a discount runs); the linked Pricing Rule is the calculation definition (how the discount is computed) — keep these concerns separate.
- [ ] **Reuse the pricing-rule scope model for campaign targeting** — For MVP, define which products/variants a campaign applies to using the existing pricing-rule scope mechanism rather than building a dedicated campaign-target table. Leave room for a dedicated targeting table later if scope needs grow more complex.
- [ ] **Build the campaign creation flow** — Implement: Create Campaign → Campaign Name → Select Products (target) → Select Discount/Pricing Rule → Set Start Time → Set End Time → Preview → Schedule. On confirmation, create the campaign in `DRAFT`, then move it to `SCHEDULED` via the Phase 10 scheduling infrastructure once start/end times are confirmed.
- [ ] **Insert Campaign Adjustment as a pricing-engine pipeline stage** — Campaign pricing must reuse the same pricing engine used elsewhere, not a separate calculator. Extend the calculation pipeline so it flows: Base Pricing → Normal Pricing Rules → Campaign Adjustment → Validation → Final Price, where the campaign's discount/adjustment is applied after normal rule calculation and before final validation.
- [ ] **Implement the campaign activation job** — At the scheduled start time, run: Validate → Calculate (via the pricing engine, including the Campaign Adjustment stage) → Execute → transition status `SCHEDULED` → `ACTIVE`. The activation must produce a pricing operation record that can be audited like any other bulk operation.
- [ ] **Capture a pre-campaign price snapshot on activation** — Before applying campaign prices, record a Pricing Snapshot of each affected variant's price as it existed immediately before the campaign changed it. This snapshot (not a reversed formula) is what restoration will use later.
- [ ] **Apply standard price protections to campaign prices** — After computing the campaign-adjusted price, run it through the same protections used elsewhere (minimum price, minimum margin, maximum discount, and any other configured protections) before allowing execution. Campaign behavior must never bypass the merchant's normal pricing protections.
- [ ] **Implement the campaign completion job** — At the scheduled end time, run: End → Check Restoration Conditions → Restore Eligible Prices → transition status `ACTIVE` → `COMPLETED`. Record the restoration result for audit.
- [ ] **Implement conflict-aware restoration** — For each variant being restored, compare the *current* Shopify price to the price the campaign applied (not to the pre-campaign snapshot directly). If they match, restore the pre-campaign snapshot price. If they differ — meaning something else changed the price during the campaign — do not overwrite it; mark the variant's restoration result `RESTORE_CONFLICT` instead of blindly restoring the original price.
- [ ] **Surface `RESTORE_CONFLICT` results for merchant decision** — When restoration produces a `RESTORE_CONFLICT`, leave the current price untouched and expose the conflict (original price, campaign-applied price, current price) to the merchant so they can explicitly decide what happens next; the system must not auto-resolve it.
- [ ] **Support campaign cancellation and failure states** — Allow a merchant to cancel a `DRAFT` or `SCHEDULED` campaign (`CANCELLED`), and transition a campaign to `FAILED` if activation or completion processing errors out, with guards on which transitions are valid from which states.
