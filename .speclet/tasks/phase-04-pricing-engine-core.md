# Phase 4: Pricing Engine Core

Status: Not Started
Source: plans/05-pricing-engine.md #1-51; plans/02-business.md #11-13,22-23

## Tasks

- [ ] **Define core price concepts and formulas** — Model Cost Price (supplier acquisition cost), Selling Price (Shopify variant price), Compare-at Price (never assumed to equal cost), Campaign Price, Profit (`sellingPrice - cost`, labeled gross/product-level profit, never "net profit"), Margin (`((sellingPrice - cost) / sellingPrice) × 100`), and Markup (`cost × markupPercentage`). Markup and margin must be distinct, non-interchangeable calculations throughout the codebase (30% markup on $100 cost → $130/23.08% margin; 30% margin → $142.86/30% margin).

- [ ] **Define PricingContext input and PricingResult output contracts, including the canonical status enum** — `PricingContext` carries variantId, currentPrice, currentCost, currency, pricingRule, protections, and context (campaign/supplier/previous-operation/rule-source). `PricingResult` carries variantId, currentPrice, proposedPrice, finalPrice, cost, projectedProfit, projectedMargin, appliedRule, status, warnings, errors. Define the single canonical `status` enum used everywhere in the system: READY, UNCHANGED, NO_COST_CHANGE, MIN_PRICE_APPLIED, MAX_PRICE_APPLIED, MARGIN_VIOLATION, MISSING_COST, MISSING_PRICE, MISSING_CURRENCY, MISSING_RULE, INVALID_PRICE, INVALID_PROTECTION_CONFIGURATION, RULE_CONFLICT, MATCHING_ERROR, CALCULATION_ERROR, RESTORE_CONFLICT, PRICE_CHANGED_SINCE_PREVIEW.

- [ ] **Implement the price calculation pipeline orchestrator with fixed step ordering** — Validate input → load current price → load cost → resolve applicable rule → calculate raw/base price → apply minimum price → apply maximum price → validate minimum margin → apply campaign adjustment (if active) → apply rounding → validate final price (re-check margin/price floor post-rounding) → calculate profit/margin → generate PricingResult. The ordering is a business contract that must stay consistent regardless of internal implementation.

- [ ] **Implement rule priority resolution and equal-priority conflict detection** — Resolve the most specific applicable rule per variant using Variant > Product > Collection > Shop/Global. If two active rules at the same scope conflict, never pick one arbitrarily — return `status = RULE_CONFLICT` and require merchant resolution.

- [ ] **Implement the CURRENT_PRICE_ADJUSTMENT strategy (percentage and fixed, increase and decrease)** — Percentage: `newPrice = currentPrice × (1 ± percentage/100)`. Fixed: `newPrice = currentPrice ± amount`. Reject a decrease that produces an invalid (zero/negative) price with `status = INVALID_PRICE`, unless configuration explicitly permits it.

- [ ] **Implement the markup strategies (percentage and fixed)** — Percentage markup: `newPrice = cost × (1 + markup/100)`. Fixed markup: `newPrice = cost + fixedMarkup`. Both require cost; missing cost must produce `MISSING_COST`, never a guess.

- [ ] **Implement the target margin strategy** — `sellingPrice = cost / (1 - targetMargin)`, e.g. cost $100 at 30% target margin → $142.857... resolved to $142.86 after currency precision. Reject configured margins ≥ 100%.

- [ ] **Implement a pluggable strategy-registry architecture** — Structure rule execution as `PricingRule → RuleStrategy` with one strategy implementation per MVP type (PercentageIncrease, PercentageDecrease, FixedIncrease, FixedDecrease, PercentageMarkup, FixedMarkup, TargetMargin) so a future rule type (e.g. AI-recommended, competitor-based) can be added without rewriting the engine.

- [ ] **Implement minimum and maximum price protections** — If calculated price < configured minimum, set finalPrice = minimum and include `MIN_PRICE_APPLIED` in status/warnings. If calculated price > configured maximum, set finalPrice = maximum and include `MAX_PRICE_APPLIED`. Both must apply before final validation, in that order (min before max).

- [ ] **Implement minimum margin protection with Protect/Enforce policy** — MVP default is **Protect**: if the calculated price violates the configured minimum margin, do not silently adjust it — return `status = MARGIN_VIOLATION`. Only apply automatic price-raising (**Enforce**) when a rule explicitly configures that behavior. A variant with no cost data can never have margin evaluated — flag it `MISSING_COST`, never assume it's safe.

- [ ] **Implement protection-configuration validation** — Before pricing execution, reject configurations where minimum price > maximum price with `status = INVALID_PROTECTION_CONFIGURATION`.

- [ ] **Implement the centralized rounding module with post-rounding re-validation** — Two independently-configurable concerns, both owned by one module (never rounded ad hoc elsewhere): (a) merchant-facing display/psychological rounding — NO_ROUNDING (default), NEAREST_INTEGER, ROUND_UP_INTEGER, ROUND_DOWN_INTEGER, CHARM_99, CHARM_95; (b) internal decimal-resolution mode for calculations that exceed currency precision (e.g. `100/0.70 = 142.857...`) — default ROUND_HALF_UP (e.g. 10.125 → 10.13). Rounding runs after protections are checked against the pre-rounded price; the pipeline must then re-check the post-rounded price against the minimum price and minimum margin floors, since rounding (e.g. charm pricing down to `.99`) can push a price back below a floor.

- [ ] **Implement decimal/money-safe currency-precision arithmetic** — All financial calculations must use a decimal/money-safe representation, never raw binary floating point (e.g. `0.1 + 0.2` must not produce an incorrect financial value). Precision must be configurable per currency rather than hard-coded to two decimals for every currency.

- [ ] **Implement final price validity checks and missing-data statuses** — Reject with `status = INVALID_PRICE` for negative price, zero price (unless explicitly configured otherwise), NaN/Infinity, or malformed decimal input; the engine must never send an invalid price to Shopify. Reject with `MISSING_COST` (required by markup/target-margin/min-margin rules), `MISSING_PRICE` (required by current-price adjustments), `MISSING_CURRENCY`, or `MISSING_RULE` (no applicable rule resolved) as appropriate — never guess missing values.

- [ ] **Implement unchanged-price, no-cost-change short-circuits, and configurable cost-decrease policy** — If `finalPrice == currentPrice`, return `status = UNCHANGED` (no Shopify update needed). If `oldCost == newCost` and no other active rule independently requires recalculation, return `status = NO_COST_CHANGE`. For a supplier cost decrease, support the merchant's configured policy explicitly — Maintain Target Margin (recalculate lower price), Preserve Current Price (no change), or Automatically Reduce Price (per configured rule) — the engine must never assume a lower cost automatically means a lower selling price.

- [ ] **Implement the campaign adjustment step and snapshot-based restoration** — Campaign pricing must reuse this same engine (no separate calculator): Base Pricing → Normal Rules → Campaign Adjustment → Validation → Final Price (e.g. $200 at 15% discount → $170), still subject to min/max price, min margin, and other protections. On campaign end, restore the price using the stored pre-campaign **snapshot**, never by reversing the formula; if the current price differs from the campaign-applied price (merchant changed it mid-campaign), return `status = RESTORE_CONFLICT` instead of blindly restoring.

- [ ] **Implement rule-source tagging, explainability trace, and audit-data capture on every result** — Every `PricingResult` must record its source (MANUAL, PRICING_RULE, SUPPLIER, CAMPAIGN, SCHEDULE, ROLLBACK) and carry a human-readable explanation of how the price was derived (current price, cost, rule, calculation, rounded/proposed price) sufficient for preview UI, debugging, audit, and support — plus the minimum audit fields: variant, old price, cost, applied rule, calculated price, final price, operation, timestamp. No pricing change may ever be unexplained.

- [ ] **Implement bulk/batch processing with per-variant isolation, partial-success aggregation, and idempotency** — Process each variant independently so one invalid variant never invalidates the batch (unless an explicit all-or-nothing policy is configured); aggregate results by status category (e.g. 970 READY / 5 MISSING_COST / 15 MARGIN_VIOLATION / 10 INVALID_PRICE) for visibility. Every operation must have an identifiable execution context so the same operation is never double-applied on retry (100→110, not 100→110→121).

- [ ] **Implement approval-eligibility classification and stale-preview/concurrent-operation conflict detection** — Only `READY` results are auto-eligible for execution by default; `MISSING_COST`, `INVALID_PRICE`, `RULE_CONFLICT`, and `INVALID_PROTECTION_CONFIGURATION` must never be executed; `MIN_PRICE_APPLIED`/`MAX_PRICE_APPLIED` are executable only with explicit merchant approval. Before execution, verify preview inputs (current price, cost, rule, protection config) haven't changed since preview — if they have, return `status = PRICE_CHANGED_SINCE_PREVIEW` and require recalculation. Detect concurrent operations targeting the same variant and apply the documented conflict policy rather than silently letting one overwrite the other.

- [ ] **Implement the rollback pricing path** — Rollback must never bypass validation: Historical Price → Current State Validation → Rollback Preview → Pricing Engine/Validation → Execution. If the historical price would now violate a currently-configured minimum margin or other protection, require merchant review instead of restoring blindly.

- [ ] **Build the unit test suite covering all required calculation paths** — Cover normal cases (valid price/cost), boundary cases (zero, very small, very large values, margin ≥ 100%), protection cases (min/max price), margin cases (at/below/above threshold), missing-data cases (cost/price/currency), rounding cases, conflict cases (price changed after preview, duplicate/conflicting rules), and bulk cases (mixed valid/invalid variants) — using the documented example test cases (100 +10% → 110; 100 -10% → 90; cost 100 +25% markup → 125; cost 100 @ 30% target margin → 142.86; calc 80/min 100 → 100; cost 100/price 110/min margin 20% → MARGIN_VIOLATION). Confirms the engine is deterministic, calls Shopify nowhere, and satisfies every item in the acceptance criteria (§50).
