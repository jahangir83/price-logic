# Phase 14: Reliability, Testing & Launch Readiness

Status: Not Started
Source: plans/06-product-requirements.md #43-50; plans/05-pricing-engine.md #49-50; plans/10-security.md #45-48

## Tasks

- [ ] **Validate asynchronous handling of long-running operations** — Confirm bulk operations (sync, pricing execution, imports) run asynchronously so the merchant is not required to keep the browser open, and confirm the UI can retrieve current operation progress at any time.
- [ ] **Validate cross-cutting reliability requirements** — Verify the system avoids duplicate pricing operations, handles retryable failures correctly, preserves operation state across restarts, records partial failures accurately, never applies a silent/unexplained Shopify change, and preserves pricing history under all these conditions.
- [ ] **Validate idempotency and concurrency for execution and workers** — Confirm retried approve/execute/import-start/campaign-create/rollback requests never double-apply their effect, and that two concurrent workers processing the same operation cannot produce duplicate Shopify mutations. This is a cross-cutting verification pass across the execution and worker layers built in earlier phases.
- [ ] **Write pricing-engine normal-case tests** — For every pricing strategy (percentage increase/decrease, fixed increase/decrease, percentage markup, fixed markup, target margin), cover valid, ordinary price and cost inputs and assert the documented example outputs (e.g. 100 +10% → 110; cost 100 +25% markup → 125; cost 100, 30% target margin → 142.86).
- [ ] **Write pricing-engine boundary-case tests** — For each strategy, cover zero, very small, and very large price/cost values and assert the engine behaves predictably (including rejecting invalid results rather than producing nonsensical prices).
- [ ] **Write pricing-engine protection-case tests** — Cover minimum price protection and maximum price protection individually and combined, including the calculated-below-minimum and calculated-above-maximum examples from the spec, and confirm an invalid protection configuration (`minimum_price > maximum_price`) is rejected with `INVALID_PROTECTION_CONFIGURATION` before pricing execution.
- [ ] **Write pricing-engine margin-case tests** — Cover margin exactly at the configured threshold, below threshold (`MARGIN_VIOLATION`), and above threshold; include a case that distinguishes markup from margin (30% markup vs. 30% margin on the same cost must yield different prices).
- [ ] **Write pricing-engine missing-data tests** — Cover missing cost (`MISSING_COST`), missing current price (`MISSING_PRICE`), missing currency (`MISSING_CURRENCY`), and no applicable rule resolved (`MISSING_RULE`); confirm the engine never guesses a value and a variant with no cost data is flagged `MISSING_COST` rather than assumed safe for margin checks.
- [ ] **Write pricing-engine rounding tests** — Cover each display-rounding strategy (`NO_ROUNDING`, `NEAREST_INTEGER`, `ROUND_UP_INTEGER`, `ROUND_DOWN_INTEGER`, `CHARM_99`, `CHARM_95`), the default `ROUND_HALF_UP` decimal-resolution mode (e.g. 10.125 → 10.13), and the post-rounding re-validation that a rounded price never ends up below its configured minimum margin or minimum price.
- [ ] **Write pricing-engine conflict-case tests** — Cover `PRICE_CHANGED_SINCE_PREVIEW` (Shopify price changed between preview and execution), `RULE_CONFLICT` (two equal-priority active rules conflict), and concurrent operations targeting the same variant not silently overwriting each other's result.
- [ ] **Write pricing-engine bulk-case tests** — Run an operation over a mixed set of valid and invalid variants and assert results are categorized correctly (e.g. `READY`, `MISSING_COST`, `MARGIN_VIOLATION`, `INVALID_PRICE` counts reported separately) and that one invalid variant never invalidates the others unless an explicit all-or-nothing policy is configured.
- [ ] **Verify pricing-engine acceptance criteria** — Confirm all MVP pricing strategies are implemented; all calculations use decimal arithmetic (never binary floating point); rounding is centralized in one place; protections (min/max price, min margin) apply consistently in the documented pipeline order; missing data is always explicit, never guessed; rule conflicts are always detected, never silently resolved; identical input always produces identical output (determinism); the engine never calls Shopify directly; and every result is explainable (variant, old price, cost, applied rule, calculated price, final price).
- [ ] **Build the security test suite** — Implement automated tests for: an unauthorized request is rejected (authentication); Shop A cannot access Shop B's data (authorization); an unapproved operation cannot update Shopify (pricing mutation); an invalid/unsigned webhook is rejected; a malformed or oversized upload is rejected (file upload); SQL and XSS payloads are safely handled (injection); a duplicate action does not execute twice (replay); and two concurrent approval/execution requests cannot cause a duplicate mutation (concurrency).
- [ ] **Run the security acceptance criteria checklist before launch** — Verify and record evidence that: tenant isolation is enforced; server-side authorization exists; Shopify credentials are protected; webhooks are verified; state-changing actions are protected; file uploads are validated; pricing inputs are validated; sensitive actions are audited; secrets never appear in logs; rate limits exist for sensitive endpoints; idempotency exists for high-impact operations; production errors never expose secrets; and backup/recovery procedures exist.
- [ ] **Verify the high-trust mutation pipeline end-to-end** — For at least one price-mutating operation type, trace and confirm the full Validate → Authorize → Preview → Approve → Execute → Verify → Audit sequence executes as designed, and confirm there is no code path that goes directly from a request to a Shopify mutation without it.
- [ ] **Run end-to-end validation of the manual pricing-rule flow** — Execute the full MVP Definition-of-Done flow with a real or staging store: install → connect → sync → select variants → create pricing rule → preview → approve → update Shopify → view history, confirming each step completes without developer intervention.
- [ ] **Run end-to-end validation of the supplier-CSV-driven flow** — Execute the full MVP Definition-of-Done flow: upload supplier CSV → match variants → detect cost changes → calculate new prices → preview → approve → update Shopify, confirming each step completes without developer intervention.
- [ ] **Validate non-functional quality bars before launch** — Confirm the MVP meets its non-functional requirements under real usage: pricing operations produce trustworthy (reliable) results; merchants can understand what will happen before execution; normal UI operations feel responsive (fast); bulk operations are processed asynchronously (scalable); and failures are inspectable and retryable where appropriate (recoverable).
- [ ] **Instrument launch success-signal tracking** — Add basic event tracking for the key early product signals: installation, activation, first successful pricing operation, repeat operations, supplier imports, scheduled operations, plan conversion, and merchant retention, so post-launch usage can be observed.
