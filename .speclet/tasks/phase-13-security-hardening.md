# Phase 13: Security Hardening

Status: Not Started
Source: plans/10-security.md #1-48; plans/06-product-requirements.md #42,45

## Tasks

- [ ] **Document the threat model** — Write down the important assets (Shopify credentials, merchant/store data, product data, pricing rules, supplier cost data, pricing operations, price history, audit logs) and the important threats (unauthorized store access, cross-tenant access, unauthorized price changes, credential leakage, forged webhooks, malicious CSV uploads, API abuse, broken authorization, replay attacks, race conditions, injection attacks). Use this as the checklist the rest of this phase's tasks are validated against.
- [ ] **Audit and close cross-tenant access gaps across every resource type** — Beyond the baseline `shop_id` scoping done in Phase 1, systematically review every endpoint/query that returns or mutates products, variants, pricing rules, pricing operations, supplier records, and price/audit history, and confirm server-side enforcement (never frontend-only filtering) that a session tied to Shop A can never read or write Shop B's records.
- [ ] **Implement endpoint-level authorization checks** — For every protected API operation, enforce the sequence Authenticated → Authorized → Correct Shop → Allowed Action. Never trust a client-supplied `shop_id`; derive shop context from the verified session. Cover at minimum: session validity, shop ownership of the target resource, and user permission for the requested action.
- [ ] **Implement state-based authorization guards** — For actions gated by resource state (e.g. an operation moving from `DRAFT` to `APPROVE`), reject the action when the resource is in an invalid state for it (e.g. `COMPLETED` → `APPROVE` must be rejected). Apply this pattern to all state-dependent mutations, not just pricing operations.
- [ ] **Implement the price-mutation protection gate** — Before any Shopify price mutation executes, require: a valid operation, correct shop, approved state, eligible price changes, and current-state re-validation. Ensure there is no code path where the frontend can directly instruct the backend to set a specific price without going through Create Operation → Approve → Server Validates → Execution Service → Shopify.
- [ ] **Implement server-side input validation for all untrusted input** — Validate IDs, numbers, currency, percentages, prices, dates, rule types, file uploads, CSV fields, search parameters, pagination, and filters on the server (never trust client-side validation alone). Include numeric-specific guards that reject NaN, Infinity, negative values where invalid, excessively large values, malformed decimals, and unexpected numeric strings; pricing values must use exact decimal handling, not floating point.
- [ ] **Audit for SQL injection safety** — Confirm every database access path uses parameterized queries or the ORM's safe query mechanisms, with no raw SQL string concatenation of user input anywhere in the codebase.
- [ ] **Implement XSS-safe rendering of merchant-controlled data** — Treat product titles, vendor names, CSV values, and any other merchant-controlled or supplier-controlled string as untrusted; ensure the UI escapes/renders these safely and never injects them as raw HTML.
- [ ] **Implement CSRF/session protection for state-changing requests** — Apply the CSRF/session protections appropriate to the chosen authentication architecture to all state-changing requests; never assume a request is trustworthy just because it originates from the app UI.
- [ ] **Implement Shopify webhook authenticity verification** — Verify every incoming webhook according to Shopify's current signature/authenticity requirements, then validate the shop before any processing. Reject invalid requests outright (flow: Verify Authenticity → Validate Shop → Check Idempotency → Process).
- [ ] **Implement webhook replay protection** — Track sufficient event identity/context (e.g. a `RECEIVED → PROCESSING → PROCESSED → FAILED` state) to detect and skip already-processed webhook deliveries so duplicate deliveries never duplicate side effects.
- [ ] **Harden the supplier CSV upload and processing pipeline** — Validate file type, size limit, row-count limit, encoding, expected columns, and per-value validity; reject malformed files and never execute uploaded content. Process large imports asynchronously (Upload → Validate → Store Safely → Create Import → Queue Job → Process → Delete Temporary File) and ensure temporary files are deleted after processing rather than retained indefinitely.
- [ ] **Implement CSV formula-injection defense and supplier cost validation** — Treat imported CSV values as data, not executable spreadsheet formulas, and handle dangerous formula-prefix characters appropriately on import/export. Separately, validate supplier cost values are numeric, finite, non-negative, within configured precision, and have a valid currency/context where required — invalid rows must never silently become valid records.
- [ ] **Implement rate limiting on sensitive endpoints** — Apply rate limits to at least: authentication endpoints, file uploads, search endpoints, pricing operation creation, pricing operation approval, and expensive sync endpoints.
- [ ] **Implement abuse-prevention controls** — Prevent a client from flooding a store with excessive pricing operations (e.g. 10,000 operations) via a combination of rate limits, input validation, operation deduplication, queue controls, and resource limits.
- [ ] **Implement idempotency support for high-impact requests** — Ensure approving an operation, starting execution, starting an import, creating a campaign, and executing a rollback are all safe to retry — a retry must never accidentally perform the action twice.
- [ ] **Implement concurrency-safe state transitions** — Use database constraints, locking, or atomic state-transition logic so that two simultaneous approval requests for the same operation result in exactly one success, and two workers executing the same operation cannot produce duplicate Shopify mutations.
- [ ] **Implement audit logging with credential-safe metadata** — Log security-sensitive actions (`APP_INSTALLED`, `APP_UNINSTALLED`, `RULE_CREATED`, `RULE_UPDATED`, `OPERATION_APPROVED`, `OPERATION_EXECUTED`, `ROLLBACK_EXECUTED`, `SHOP_CONNECTION_CHANGED`, `IMPORT_STARTED`, etc.). Ensure audit log entries never contain access tokens, client secrets, passwords, encryption keys, or other full sensitive credentials — filter metadata before writing.
- [ ] **Implement safe error responses and correlation IDs** — Production error responses must never expose database connection strings, stack traces, Shopify tokens, or internal filesystem paths to the client; return a safe error plus an internal correlation ID. Propagate traceable identifiers (`request_id`, `operation_id`, `job_id`) across the API request → database record → queue job → Shopify request → result chain to support debugging.
- [ ] **Implement secret-free structured logging** — Ensure application logs use structured, non-sensitive fields (e.g. `operation_id`, `shop_id`, `status`, `error_code`) and never log raw secrets such as access tokens.
- [ ] **Harden database access and establish backup/recovery procedures** — Use strong credentials, encrypted connections where supported, restricted network access, and least-privileged database users; run migrations through a controlled process. Set up automated, encrypted, access-controlled backups and periodically test restores. Define recovery procedures for database failure, queue failure, Shopify outage, partial pricing execution, and failed deployment, ensuring pricing operations remain recoverable after worker/application restarts.
- [ ] **Set up dependency security management** — Keep dependencies version-controlled and regularly updated, scan them for known vulnerabilities, remove unused dependencies, and avoid adding packages for trivial functionality.
- [ ] **Lock down production configuration and enforce secure defaults** — Disable debug mode, verbose error responses, development credentials, test endpoints, and unprotected admin routes in production. Implement secure-by-default behavior throughout: no pricing rule → no price change; no approval → no execution; invalid cost → no repricing; invalid webhook → reject; unknown tenant → reject.
- [ ] **Scope components to least privilege and enforce internal service boundaries** — Ensure each component (e.g. the pricing worker) has only the permissions it needs and nothing unrelated. For sensitive internal service calls, require established caller identity, operation authorization, and validated input — services must not trust each other blindly.
- [ ] **Implement secret and credential rotation support** — Support rotating application secrets, encryption keys (where the architecture allows), and Shopify credentials on reauthorization, without ever exposing secrets to application users during rotation.
